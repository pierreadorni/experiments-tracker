### Executor (`gateway_client.py`, 724 lines)

Eight pollers run in parallel. `commands`, `project_commands`,
`project_settings_commands`, `project_memory`, `autopilot` and `maintenance` each
fetch their own queue. `publish_outbox` and `replay_events` push
`public_projection` plus inbox rows per outbox event, and `upload_artifacts` sends
registered artifacts. `heartbeat` posts the status, with the project catalog and
capability flags. A command is committed in SQLite, or its refusal is saved in
`rejected_gateway_commands`, before ack or reject. Tests:
`tests/test_gateway_client.py` (1,118 lines), plus parts of `test_maintenance.py` and
`test_iteration_autopilot.py`.

### Local FastAPI (`api.py`, 523 lines) and UI data paths

FastAPI serves the same URL paths as the Worker for experiments, commands, inbox,
status, projects, knowledge, Autopilot and artifacts. Responses come straight from
SQLite. Domain refusals are synchronous 409s. It also has local-only routes
(`/api/maintenance/internal|step|stop|releases`, `/api/projects/agents-template`,
`/api/experiments/{id}/reports`). The Worker has hosted-only push routes.

`web/src` calls these paths through `api()`/`command()` in `api.ts`. The data paths
differ by host as follows:

- Hosted views carry Worker-added fields: `pending_commands`, `pending_messages`,
  merged notes and `remote_published`.
- A hosted create shows a placeholder projection fabricated by the Worker.
- Receipt states differ: hosted `waiting_for_executor|applied|rejected`; local
  passes the store state through.
- Two `status.mode === 'gateway'` branches in `main.tsx` (mode label and upload
  state) depend on the host.

## 2. Target (C9)

**D1 (new append-only migration `0010`).** Old tables stay and become unused.

| Table | Columns | Purpose |
|---|---|---|
| `relay_projections` | `key` PK, `executor_id`, `revision` int, `payload` text (NULL = tombstone), `digest`, `notify_fingerprint`, `updated_at` | every published view |
| `relay_commands` | `request_id` PK, `executor_id`, `kind`, `target` (nullable key), `payload`, `state` (`pending/applied/rejected`), `result`, `error`, `received_at`, `settled_at`; index (`executor_id`,`state`,`received_at`) | one command queue |
| `relay_follows` | (`subscription_id` → `push_subscriptions`, `key`) unique, `created_at` | push follows by key |
| `relay_push_outbox` | as `push_outbox`, with `key` instead of `experiment_id` | push deliveries |

`push_subscriptions` and `push_receipts` are reused unchanged; they hold no
projection foreign key. The names `projections` and `commands` are already taken by
incompatible tables: `commands` requires an experiment and its FK prevents project,
settings, memory, Autopilot and maintenance commands. Reusing them would need a
table rebuild.

**R2.** Blobs live at `blobs/<artifact_id>` with custom metadata `sha256`, `size`,
`media_type`, `name` and `owner_key`. One blob path covers experiment artifacts,
report figures and Autopilot documents and files.

**Keyspace.** `experiment:<uuid>`, `conversation:<uuid>:<seq, 10 digits>`,
`projects`, `status`, `inbox`, `knowledge:<pid>`, `knowledge-report:<pid>:<v>`,
`autopilot:<pid>`, `maintenance`.

**Executor publication.** One Python builder, `publish/projections.py` (C11), builds
every document. Hosted publication and local reads both use it.

- An experiment document is `public_projection` plus its own notes, the
  executor-known `remote_published` and inbox rows. Its revision is
  `experiments.revision`, unchanged.
- Aggregate documents use `max(now_ms, last_acked + 1)` and are published only when
  their digest changes. This is monotonic by construction for the single writer.
- The envelope is `{schema_version: 1, key, revision, document, notify?}`.
  `notify = {fingerprint, title, body, url, alert, targets: [key…]}` is computed by
  the Python port of `experimentNotification` and by Autopilot.
- Dirty tracking reuses the SQLite `outbox`. The current event's row is marked
  delivered when its revision is acknowledged; older rows are marked superseded.
  `GET /api/executor/relay/revisions` returns `{key: [revision, digest]}`, so a
  restart or a fresh table diff-publishes what is missing. This also drives the
  backfill. No new SQLite table is needed.
- Blobs are uploaded before the document revision that marks them published.

**Worker.** It checks auth, size, executor identity and monotonic revision only.

| Route | Credential | Check |
|---|---|---|
| `PUT /api/executor/relay/projections/<key>` | executor | ≤1 MiB; key regex; `revision > stored` accepted; equal revision and digest → idempotent 200; otherwise 409 stale. If `notify.fingerprint` changed, enqueue push for followers of `targets`. |
| `GET /api/executor/relay/revisions` | executor | — |
| `PUT /api/executor/relay/blobs/<id>` | executor | ≤10 MiB; body sha256/size equals headers (transport integrity); an id is immutable |
| `GET /api/executor/relay/commands`, `POST …/receipts` | executor | ≤20 per batch; terminal receipts are immutable (identical repeat OK, conflicting 409) |
| `GET /api/projections/<key>`, `GET /api/projections?prefix=&before=&limit=` | browser | tombstones 404/omitted; response `{key, revision, updated_at, document}` |
| `POST /api/commands`, `GET /api/commands/<id>`, `GET /api/commands?state=pending` | browser | ≤64 KiB; `kind` matches `^[a-z_]{1,40}$`; same `request_id` with the same bytes → same receipt, different bytes → 409 |
| `GET /api/blobs/<id>` | browser | owner key must be live; sandbox CSP as today |
| push config/status/forget/follow (by key), session, static assets | browser | unchanged |

`authorize()` stays as is: `/api/executor/*` takes only `EXECUTOR_TOKEN`; every
other `/api/*` takes only Sites identity (or `USER_TOKEN` in token mode). An
executor token never authorizes a browser route, and the tests assert both
directions.

**Commands and receipts.** The executor fetches pending relay commands and
dispatches each by kind through one function, `dispatch(kind, target, payload,
origin)`. It calls the existing idempotent handlers: `store.command`, project
create/settings, knowledge, Autopilot and maintenance.

- An accepted command is committed in the same SQLite transaction as its events and
  outbox rows.
- A refusal is saved in `rejected_gateway_commands`, together with a local inbox
  notice (moved from the Worker's reject route).
- The receipt (`applied` plus `result`, or `rejected` plus `error`) is posted only
  after that commit. A lost receipt response is redelivered and answered from the
  saved outcome.
- A request id replayed across the cutover reaches `store.command` with the same
  model-validated payload and gets the prior result.

**Local FastAPI.** It serves the same projection, command and blob routes, building
documents on demand with the same builder. `POST /api/commands` calls `dispatch`
synchronously and returns the same receipt shape, already terminal.
`GET /api/session` reports `{host: "gateway"|"local"}` and replaces
`status.mode === 'gateway'`.

## 3. Migration and deployment order

There are two deployables: the Worker (W, which bundles the hosted UI) and the
executor release (E, which ships the local UI in `web/dist`). Old endpoints and
old tables stay readable until the named removal cards.

| Step | Ships | Safe if the other side is older? | Rollback |
|---|---|---|---|
| W1 | `0010`; relay executor and browser routes, beside the old ones (T5.2a) | Yes. Old executors and the old UI never call them. | Redeploy the previous Worker. `0010` tables stay, unused. |
| E1 | Builder, dual publication, relay command poller, local relay routes (T5.2b-d) | Yes, either order. A 404 on a relay route means "relay unsupported": quiet backoff, no error, no outbox change. | Normal executor rollback. No SQLite schema change, so it is clean. |
| — | **Gate:** the revisions manifest covers every live key and old queues still drain (heartbeat reports `relay_missing = 0`) | — | — |
| W2 + E2 | UI on relay routes (T5.2e); push by key and migration `0011` copying `push_follows` into `relay_follows` (T5.2f) | **E1 must precede W2.** Otherwise hosted views are empty and relay commands wait, although no command is lost. | W2 → W1: the old UI reads old tables, still current through dual publication. Relay commands still drain through E1. Follows made under W2 are lost; the owner re-follows. |
| E3 | Removal of the dual path in the executor (T5.2g) | **W2 must precede E3**, and old queues must be empty (the old fetch routes return nothing). Otherwise old-UI commands strand. | E3 → E2 restores dual publication. |
| W3 | Removal of old Worker routes and code (T5.2h, T5.2i) | **E3 must precede W3.** Otherwise E2 logs 404s on old routes; relay still works. | W3 → W2. Old tables are stale, but W2 no longer reads them. |

Required order: **W1 and E1 in either order, then the backfill gate, then
E1 → W2 (E2 any time after E1), then W2 → E3 → W3.** The dual-publication window runs from E1 to E3; T5.2g and
T5.2h/i are its named removal cards. The phase is not done while they are pending.

The backfill is the first E1 tick: the manifest is empty, so every live key
publishes, at most N documents per tick (§5, decision 5). Commands posted to the old
`commands` table before W2 drain through E1's old poller. Before E3, the operator
confirms that the old queues are empty.

## 5. Open owner decisions

**Approved 2026-11-22:** the owner approved every recommended default below.

1. **New D1 tables:** `relay_projections`, `relay_commands`, `relay_follows`,
   `relay_push_outbox` in `0010`, and a data-only `0011`. *Recommend: approve.* The
   alternative, rebuilding the old tables, violates append-only migrations.
2. **Asynchronous refusals when hosted.** The Worker drops every synchronous domain
   409 and every executor capability gate. Refusals arrive through the receipt and an
   inbox notice; local mode returns the same, already terminal, receipt.
   *Recommend: approve.* The UI disables impossible actions from projection state.
3. **No fabricated placeholder.** A pending create shows from the command queue.
   *Recommend: approve.*
4. **Error responses:** 413 over a cap and 409 `stale revision`, plus a new 429 when
   more than 500 commands are pending per executor. *Recommend: approve all three;
   429 is the only new code.*
5. **Caps:** documents ≤1 MiB (today's body cap, below D1's 2 MB row limit);
   commands ≤64 KiB; blobs ≤10 MiB (today's); backfill ≤20 documents per tick.
   *Recommend these values, as constants, not config keys.*
6. **Kind validation:** the Worker checks only the `kind` regex, and the executor
   refuses unknown kinds. *Recommend: approve.* New kinds then need no Worker release.
7. **Notification text moves to Python**, carried in the envelope's `notify` field
   (a new wire field). *Recommend: approve.*
8. **No new config key, environment variable or SQLite table.** Relay support is
   detected by 404, and the revisions manifest replaces a local publication ledger.
   *Recommend: approve.*
9. **Old D1 tables stay unused.** There is no DROP; purging their data would be a
   separate owner-approved migration. *Recommend: leave them.*
10. **Order with T5.1 (Autopilot).** *Recommend landing T5.2a-d first*, so T5.1
    publishes `autopilot:<pid>` documents and adds no Worker tables.

## 6. Risks

- **Slower hosted errors.** A refusal now waits one poll (5 s), or the executor's
  return. The UI must show "waiting for executor" clearly.
- **Follows during the W2 window.** A follow made between applying `0011` and
  deploying W2, or under a rolled-back W2, can be lost. The owner re-follows.
- **Restore.** After a stopped-writer SQLite restore, experiment revisions can fall
  below the stored ones, and the Worker refuses them as stale (same as today).
  Recovery is a compatible forward publish at a higher revision, never a D1 rewrite.
- **Merge conflicts.** `gateway_client.py`, `index.ts` and `main.tsx` are hot files:
  run their cards in sequence.
- **Live acceptance is separate.** Miniflare and the smoke tests do not establish
  hosted acceptance: W1-W3 still need the `docs/gateway.md` checks on the owner's
  Site.
