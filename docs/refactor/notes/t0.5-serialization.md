# T0.5: global agent serialization

Investigated 2026-11-12 against `f7b9ba2`. Line numbers below refer to that
revision. This is a source investigation; runtime code is unchanged.

## Decision

Move the implementation into **T1.6**, split into reservation plumbing, mixed-role
admission and recovery scenarios. A guard-only T0.5b is unsafe. Multiple generic
experiments already use independent agents when `codex.max_sessions > 1`.
Autopilot, project supervision and conversations still share the owner's primary
agent. Removing their global guards requires assigning each role a slot throughout
dispatch, callbacks, interruption and recovery.

## Agent ownership today

- `Workflow.__init__` stores its agent, installs request/activity/quota callbacks
  and creates its role controllers (`workflow.py:75-124`).
- `start_agent_pool` creates one distinct `CodexAgent` and Workflow per additional
  slot, with a separate `agent-slot-N` runtime directory; demo slots instantiate a
  separate demo agent (`workflow.py:250-264`). Lanes share the owner's quota gate,
  controller bridge, ResearchController and submission lock.
- Generic `agent_stage` calls delegate through `agent_lane`
  (`workflow.py:2068-2071`). That allocator preserves an assignment with an active
  action and otherwise chooses a lane without `agent_task`
  (`workflow.py:238-248`). Extra sessions therefore provide experiment concurrency,
  but they do not allocate slots for other roles.
- The owner's ResearchController uses `wf.agent.session/begin/finish`
  (`autopilot_controller.py:376-429`). ProjectSupervisor similarly binds
  `agent = self.workflow.agent` (`knowledge.py:761-789`). Conversation binds
  `self.workflow.agent` (`conversation.py:488-553`), and its admission writes the
  owner's `active_action` and `agent_task` (`conversation.py:440-441`). None of
  these role paths allocates a separate CodexAgent.

## The four blockers

| Blocker and evidence | Which agent it protects and why | Safe to remove with multiple sessions? |
|---|---|---|
| `self.agent_task`, `workflow.py:2498-2500` | The current lane's `self.agent`. A lane has one task and one active action; the primary lane also hosts conversation/title work. | **No.** This is a lane-local exclusion, not a global experiment lock. Keep one live turn per agent. |
| `research.busy`, `workflow.py:2514-2515`; definition `autopilot_controller.py:29-36` | The owner's primary agent. Busy means an in-memory research task or any durable Autopilot action in `dispatching`, `running` or `uncertain`. Every experiment lane shares that ResearchController, so this blocks all lanes. | **No guard-only removal.** Other agents could do independent work, but the primary agent must remain reserved and unresolved research identities must survive task completion/restart. |
| `supervisor.blocks_dispatch`, definition `knowledge.py:575-582`; callers `workflow.py:565-566,590-593` | The owner's primary agent. A supervisor task or durable `project_turns` row in `dispatching`, `running` or `uncertain` empties the experiment advancement list and skips conversation/title/controller advancement. | **No guard-only removal.** It blocks more than inference admission, including deterministic experiment advancement. Separate that progression from admission only after primary-agent ownership is explicit. |
| `active_sql`, `workflow.py:2501-2509` | A durable `agent_actions` exclusion before using the current lane's agent. It excludes other dispatching/running/uncertain actions globally for one session; with multiple sessions it already appends `AND experiment_id=?`. | **Keep.** It already permits unrelated experiments with multiple sessions. Removing its per-experiment scope would permit overlapping work while an earlier outcome remains unknown. It does not account for the separate project/research action tables. |

## Why distinct threads are insufficient

`CodexAgent` has one `active` field (`codex_client.py:205`), set by `begin`
(`342,371`) and cleared by `finish` (`443`). `finish` consumes a single shared
`server.events` queue (`383`) and discards other-thread notifications (`394-395`).
Two overlapping finishes on one instance can consume and discard each other's
events. Activity timing and request callbacks also assume one active owner.

The Workflow request router first looks up its `active_action`, then falls back
to the owner's active ResearchController (`workflow.py:469-472`). Simply passing
another agent to `dispatch` would leave callback and input-answer routing wrong.
Experiment answers currently go through the owner's agent (`workflow.py:529-536`);
research answers use its owner's agent (`autopilot_controller.py:142-157`). A slot
assignment must cover the connection owning each pending RPC as well as the turn.

## Reciprocal waits and related paths

- Research waits for supervisor and **any** lane task
  (`autopilot_controller.py:225-226`); non-weekly project turns and queued/waiting/
  running discussions take priority (`227-230`). Its recovery and interruption use
  the primary agent (`172-175,207-218`).
- Supervisor waits for research before even processing its task/recovery
  (`knowledge.py:674-683`). New supervisor dispatch also waits for every lane task
  or any dispatching/running/uncertain experiment action (`742-746`). Its recovery
  and interruption use the primary agent (`595,728`).
- Conversation admission waits for the primary task **or any** unresolved active
  experiment action (`conversation.py:393-396`), regardless of session count.
  Recovery/interrupt use the primary agent too (`360-372`). This is another global
  exclusion even though experiment admission is already scoped per experiment.
- Titles occupy the primary task (`workflow.py:702-703,749-750`) and retain a
  research-busy check in `dispatch_title` (`766-769`). Monitor/controller actions
  must also enter the same reservation mechanism before global guards disappear.
- Quota refresh interrupts research, supervisor and lane experiment actions through
  their present owners (`workflow.py:421-449`); shutdown similarly closes the
  existing role tasks and lane agents (`workflow.py:4288-4325`). Preserve this
  coverage when ownership moves.

## Smallest safe implementation: T1.6

1. Introduce shared slot reservations around the existing agents, without changing
   scheduling behavior. A reservation names the role, owner key, durable action and
   agent. Route requests, replies, activity, interruption, reconciliation and
   shutdown through that assignment. Preserve existing action tables and exact
   thread/turn identities; no scientific-contract change is needed.
2. Move experiment, research, supervisor, conversation, title and monitor admission
   onto those reservations. Then replace global busy checks with slot availability
   and owner exclusion, retaining C4 priority and existing quota/authorization
   checks. Keep experiment and project ownership explicit so independent projects
   can proceed without overlapping turns for the same owner. Reserve a slot before
   asynchronous dispatch; a task finishing is not proof that its durable action
   settled. Reconstruct reservations before admission after restart, including
   uncertain outcomes and configuration changes in session count.
3. Prove mixed-role concurrency and recovery with synthetic scenarios: experiment
   plus research, experiment plus supervisor, discussion plus unrelated experiment,
   one-slot serialization, same-owner exclusion, lost outcome/restart, correct
   callback/answer/interrupt routing, quota interruption and shutdown across all
   occupied slots. An unknown outcome must never authorize a duplicate turn.

Existing evidence is narrower: `tests/test_controller.py:449-496`,
`test_configured_sessions_let_another_plan_progress_while_one_turn_waits`, asserts
two simultaneous generic planning actions with two slots, a shared quota gate and
zero scheduler submissions. It does not establish mixed-role safety. T0.5 adds no
runtime tests because it changes documentation only; the existing concurrency
test and full Python suite are the regression checks. Synthetic demo/test results
do not establish live managed-runtime or scheduler acceptance.
