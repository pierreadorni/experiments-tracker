# T1.1a: inventory of legacy-contract branches

Investigated 2026-11-13 against `d3a636e`. Line numbers refer to that revision.
This is a source investigation: no runtime code was changed.

Scope: every branch conditioned on the legacy predicates named in the T1.1a card
(`recipe_id == "toy_compare_v1"`, absent `planning_version`, plan `schema_version`
< 3, `iteration.enabled(exp)` false, `strict_reproducibility`, contract ≤2
`auto_repair` / `repairs/` roots, `Preparation`, `freeze_recipe`,
`verify_snapshot`, the `validate` stage, `dependencies()`), plus the background
paths in `tick()` that can still dispatch work for an experiment that `advance()`
would skip.

## Legend

Each entry carries:

- **Task** – the deletion card that owns it (T1.1d `advance()`, e `agent_stage`
  legacy `prepare`/`Preparation`, f validate stage and `strict_reproducibility`,
  g contract ≤2 repair and `repairs/` roots, h `artifacts.py` freeze/verify
  helpers and `recipes/toy_compare`).
- **Class**
  - **exec** – execution-side code, not an archive reader. Delete only the
    explicitly identified legacy arm after archival; shared entry points and
    contract-3 arms remain. This label alone is not deletion authorization.
  - **reader** – reads saved legacy records (display, export, verification).
    Still required after archiving: archived reports, artifacts and events stay
    viewable (`design.md` C10).
  - **schema** – a model or SQL shape that saved rows already contain. Deleting
    it would break reads of saved rows or change saved identities.
  - **keep-3** – contract-3 code with no legacy half; listed in §18 only so the
    index is exhaustive. Never a deletion.

Two behaviours genuinely need an owner answer (in-flight work, fixture budget);
they are listed in §17.3 and marked `**unspecified**` where they appear. Nothing
else in this note is a request for a decision: the rest of §15 and §17.4 are
consequences of the card, not choices.

Consequences worth stating up front:

1. `strict_reproducibility` has no writer in the present source (reads only, §5),
   so no current command sets it; whether a saved contract carries it cannot be
   settled from the source, and this note makes no such claim. That distinction
   does not decide the deletion: a saved contract keeps its meaning because the
   blob is never rewritten, and a legacy experiment stops advancing after
   archiving, so the flag becomes inert without being reinterpreted. The only
   direct coverage is the `strict` cases in `test_local_outputs.py` and
   `test_temporary_outputs.py`.
2. `auto_repair` is **not** a legacy-only key. Contract 3 selective repair reuses
   the same two contract keys (`early_repair.py:113-116`), so the key, its
   projection summary (`store.py:42-55`) and `projects.root()`'s `records/`
   branch must stay. Only the *legacy semantics* of the key are removable.

A third shape matters for the deletion cards: `tests/conftest.py:40-66` builds
`agent_experiment_v1` contracts with `execution_contract` **popped** but
`planning_version: 1`, `brief_driven`, `reporting_version` and
`resource_policy_version: 2` retained. The fixture reproduces the legacy shape
(a generic recipe without `execution_contract`, carrying `planning_version`);
`store.py:979-991` writes both keys together on the create path, so the fixture
produces that shape by removal rather than by creation. This note makes no claim
about imported or pre-public saved records: "contract ≤2 generic" below means "a
saved generic experiment without `execution_contract`", which the fixture
reproduces.

Because `planning_version` is independent of the contract, **"plan/prepare" and
"continuation bookkeeping" are not contract-3 markers**. Every branch keyed on
`planning_version` (`workflow.py:1177`, `2084`, `store.py:803`) is live for the
fixture shape too, so those are shared/schema branches, not deletions.
