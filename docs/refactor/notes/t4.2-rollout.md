# T4.2: research tools through the existing controller

The contract-4 tool list is separate from the contract-3 stage tool list. Reuse
`Controller`'s existing stdio-to-Unix-socket bridge and the pool's saved action
ownership. An advertised tool is not authorization: check the live owned action,
experiment, exact scope and relevant pause/maintenance gates in the backend.
Validate with a strict Pydantic input model before any effect. No tool launches a
separate managed turn. Each capability must work against scripted runtime and
scheduler boundaries before it is counted as done.

## Order and ownership of effects

1. **`cluster_info` and job reads:** serve only a bounded cache or exact own saved
   job records and bounded local log tails. No discovery RPC, remote SSH, stage
   mutation or receipt write. A UUID scopes the request; repeating a read may
   return newer facts, but never causes a side effect.
2. **Checkpoint, question, report and artifact tools:** keep receipts bound to
   request ID, experiment, tool and exact input. Reuse existing natural keys or
   versioned saved effects; reject mismatches instead of applying them. A
   checkpoint is private session context, not a public note or report. Check
   publication/export readers before using events to store its contents.
   `ask_owner` needs a real existing owner obligation and inbox evidence;
   distinguish a durable request (next-turn input) from a live app-server RPC.
3. **`submit_job`:** separate eligibility, immutable export, saved intent and
   Slurm boundary. Reuse resource validation, preflight, commit pinning,
   cancellation, and exact comment/identity recovery. `jobs.stage_id` is a
   required FK to `stages`; compatibility rows could serve as job identities,
   never as a second graph or dispatch authority, and must have a retirement
   plan if temporary. Use no new table/migration without the owner’s approval.
   The observer must route contract-4 jobs independently from contract-3 stage
   logic; do not loosen a contract-3 `iteration.enabled` check to achieve that.
   Submission remains closed until the T4.4 approval check is wired and tested
   at the effect boundary, including lost-response, cancellation and pause.
4. **Cancellation and integration:** reuse existing exact-intent and exact
   candidate behavior. A tool result means queued/accepted, not necessarily
   externally complete. No retry while the existing effect is uncertain.

## Approval and submission implementation boundaries

- **T4.4 manual authority:** retain the exact experiment ID, project ID, original
  brief, request UUID and bounded proposed objective in a durable approval
  request receipt. Compare those saved values; no objective hash. Accept only an
  applied owner `answer` command with literal `accept`, backed by the exact
  satisfied request obligation. An ordinary question or a tool's own response
  cannot authorize compute. Keep the receipt after the pending request is
  consumed; the writer must refuse changing a recorded approval decision.
- **Contract-4 job observation:** first settle exact saved scheduler IDs in isolation.
  A terminal transition, its obligation and its wake commit together. A healthy
  job does not wake the agent. Missing IDs use the existing resolver when that
  path is wired; never infer a retry from missing or stale scheduler evidence.
- **Submission:** validate the approval before committing source, exporting it,
  or calling scheduler preflight. Recheck before saving the dispatch intent and
  crossing the scheduler boundary. Match resource and pause gates to the saved
  experiment. Wire the tool only after the observer and uncertain-intent recovery
  work in an isolated end-to-end scenario. Leave contract 3's stage path alone.

T4.3 owns durable wake consumption, debounce and timers. Changes in a generic
revision or polling cadence are not wake signals. T4.5 owns hosted/UI parity;
T4.7 still requires explicit owner authorization.
