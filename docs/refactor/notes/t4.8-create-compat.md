# T4.8 create compatibility: bind intent before switching the default

Contract 3 remains the default and project `research_loop` remains opt-in.
The executor and Worker source now accept an explicit C4 create; this note
records the compatibility rules for the remaining client and cutover work.

## Wire facts and the delayed-create hazard

Before the explicit-create change, the create path had no execution-contract
binding on the wire. The unbound path still has these properties:

- `web/src/main.tsx` submits `schema_version: 1`, a request UUID, and create
  fields such as `recipe_id`, `workspace_mode`, `execution`, and an optional
  reference. `schema_version` versions the transport envelope; it does not mean
  execution contract 1, 3, or 4.
- `gateway/src/index.ts` validates that request with strict `createSchema`,
  stores the exact JSON payload in `commands`, and returns the same saved outcome
  for an exact `request_id`/payload replay. A new create also immediately gets a
  hosted `waiting_for_executor` projection whose placeholder contract is 3.
  `/api/executor/commands` later returns the saved payload unchanged.
- For an unbound payload, the Worker still uses placeholder C3 and the executor
  chooses the contract at application from the current project flag and
  eligibility. An explicit C4 payload instead queues a C4 placeholder and is
  applied as C4 or rejected, without fallback.
- Worker validation uses `.strict()`, and the executor create model is strict.
  An older Worker/executor is therefore not a safe place to send a newly added
  discriminator: it should reject an unknown field, rather than be relied on to
  ignore or reinterpret it. Existing capability checks (for example
  `executorSupports()` for cancellation) use the last saved executor heartbeat;
  they are not a generic create-contract negotiation today.

Consequently, a hosted create accepted before an upgrade can sit pending, then
reach a newer executor after its project flag/default has changed. The same
unbound payload can acquire a different contract depending on delivery timing.
The hosted placeholder may also continue to describe it as contract 3. The
transport `schema_version: 1` cannot disambiguate this. The existing exact replay
behavior is valuable: an already-applied request must return its recorded
outcome, not re-run today's selection policy.

## Compatibility rule to implement

Introduce a create-intent discriminator distinct from transport `schema_version`
(`execution_contract: 4`). The executor and Worker now support this explicit
value. The cutover still needs these semantics:

1. **Absent means legacy/unbound.** Never infer a future contract from absence,
   the current default, or a project flag. Preserve the saved legacy interpretation
   for accepted pending requests, or refuse them at a defined cutover with a
   clear, durable rejection before local application. Do not silently upgrade a
   delayed legacy request to contract 4.
2. **Explicit supported value means exactly that intent.** If the requester asks
   for contract 4, create contract 4 or refuse it with an actionable incompatibility
   reason. Do not fall back to contract 3 when project eligibility, executor
   support, reference/workspace constraints, or deployment support is missing.
3. **Unknown/future values are rejected, never treated as absent or as the
   current default.** A new Worker should strictly distinguish absent legacy
   traffic from an explicit unsupported future version.
4. **Exact replay is outcome replay.** If the request UUID already has a saved
   command, compare kind, exact payload, and experiment identity as today and
   return its saved pending/rejected/applied result. Do not re-check today's
   capability, project setting, default, or contract selection for an exact
   already-applied replay. Same UUID with altered payload remains conflict.

The implementation should bind the requested contract to local saved creation
and the hosted placeholder/projection before any later delivery. It must also
preserve older Worker behavior deliberately: do not send the new discriminator
until a Worker version known to accept and preserve it is installed. An older
strict Worker should reject a future explicit request, not silently queue it as
legacy; caller-visible handling must retain the same request identity and explain
that the gateway needs upgrading. Capability reporting/gating must be deployed
before the UI starts emitting explicit contract-4 creates. A stale/missing
capability is a refusal/hold, not permission to send an unbound request instead.

## Staged implementation and validation

1. **Specify and freeze compatibility semantics.** Owner chooses the wire
   discriminator and exact contract-3 compatibility policy for legacy pending
   requests at the default-switch boundary. Keep `schema_version: 1` meaning
   unchanged. Document the Worker/executor minimum versions and whether stale
   legacy requests are applied as C3 or rejected before application. Do not
   alter defaults in this stage.
2. **Worker-first compatibility support.** Extend Worker create parsing/receipts
   and projection construction to preserve an explicit intent while retaining
   absent-field legacy parsing. Add a create-specific executor capability from
   the saved heartbeat and refuse explicit contract-4 requests unless a capable
   executor is present. Make parsing strict for unknown explicit values. Deploy
   this Worker support before any client sends the new field. No executor
   implementation or default switch is implied by deploying it.
3. **Executor create binding.** Extend the strict create model and local create
   transaction to accept the explicit intent, validate supported intent and
   eligibility, persist the exact chosen execution contract, and ensure an
   exact replay returns the saved result without repeating selection. Keep an
   absent field on the existing legacy path, including existing default behavior
   while the default is still C3. Exercise old payload fixture compatibility and
   both origins (local API and gateway command).
4. **Client capability gate.** Only after Worker and executor support is
   available, have the new client send the explicit intent for contract-4
   creates. Capability traffic must be authoritative for the specific executor
   receiving the command, fresh enough under the chosen policy, and fail closed
   when absent/stale. A gateway with older executor heartbeat must offer a clear
   unavailable/refusal response, not queue an intent that may later be re-read
   differently. Keep existing project eligibility and reference/workspace
   refusals; do not broaden contract-4 support in this compatibility card.
5. **Delayed-command and rollout boundary.** Before changing any default, inventory
   pending hosted creates, locally pending create commands, and already-created
   experiments. Test that a queued unbound request does not become C4 after the
   switch; explicit C4 remains C4 across delivery/restart; old Worker/executor
   rejects rather than reinterprets an explicit value; and exact applied replay
   remains applied despite later settings/capability changes. Default switch and
   C3 drain/engine retirement remain separate owner-authorized work per
   `t4.8-rollout.md`.

### Test surfaces

- **Worker unit/integration (`gateway/test/gateway.mjs`):** strict schema cases
  for absent, supported, unknown and malformed intent; exact request replay while
  pending and after ack; same-ID/different-payload conflict; projection contract
  consistency; capability missing/stale/old executor refusal; command redelivery
  preserving the payload; explicit create against an older Worker's strict parser.
- **Executor (`tests/test_gateway_client.py`, `tests/test_contract_immutability.py`,
  `tests/test_research_create.py`):** legacy payloads still parse; explicit
  contract intent yields exactly the requested supported contract or a refusal;
  no fallback; exact applied replay does not recalculate after project flag change;
  pending/rejected identities are stable; local and gateway-origin creates agree.
- **API/UI (`tests/test_api.py`, web create tests / `web/src/main.tsx`):** old
  clients remain compatible through the selected legacy policy; new clients send
  explicit intent only after advertised capability; unsupported capability yields
  visible refusal without resubmitting under a new UUID or dropping the intent.
- **Cross-version delayed-wire fixture:** capture a literal old unbound payload,
  enqueue it through the Worker, upgrade the Worker/executor/client in stages,
  then deliver/replay it. Separately verify an explicit future-value payload is
  rejected by a strict older Worker and is never downgraded. Use scripted local
  boundaries only; no hosted deployment or live access is part of these tests.

## Owner decisions still required

- Drain pending hosted creates before the switch. At cutover, enable the
  executor’s tested refusal of late unbound hosted creates; do not reinterpret
  them as C4. Already-applied requests continue to replay their saved outcome.
  The refusal is disabled in the current C3-default source.
- Whether an older gateway/client should show a hard upgrade-required error or
  hide/disable the C4 option. It must not strip the explicit intent and retry as
  legacy.

The Worker requires `execution_contract_create: 4` in a heartbeat received for
its executor within 90 seconds before queuing a new explicit C4 create. Exact
replay is checked first. The browser sends the explicit field for projects
advertised as opted in, rechecks status at submission, and does not retry as
C3 if refused. Source publication does not deploy either component.
