## 2. Disposition vocabulary

- **ENTRY** — a saved-contract guard that an entry point keeps because a frozen
  record really reaches it: a user/gateway command, a CLI reconciliation, a tool
  call, a stage/dispatch entry, or a sweep that iterates saved records. It is the
  archived refusal, not a re-check. `agent_stage:2188` is recorded as ENTRY because
  card c/d keeps one guard per entry point, even though `advance:1377` currently
  returns first (row 34 of §4).
- **SETTLE** — legacy settlement: the site records scheduler facts or a turn
  identity for a frozen record, completes a saved action without adopting anything,
  or declines to advance it. Reachable for a frozen record by design.
- **READER** — reachable for a completed or archived record because the engine must
  read or skip it (queued reports, discussion evidence, published reports, sweeps
  over all experiments). The frozen record takes the `False` arm and the reader
  keeps its saved evidence-revision scope, or the sweep skips it.
- **DEAD** — the frozen guard is **dominated**: an earlier guard in the same call
  chain (or the same call) already returns/raises for a frozen record, and §6 proves
  the saved key cannot change between the two lines. Deleting the guarded arm
  changes no reachable behaviour.
- **HELPER** — the shared predicate/definition itself. It stays.

Basis **D** (dominated) is the only basis used for DEAD in this revision. There is
no "redundant by record shape" basis: **no disposition here infers a row's shape
from the current creator**. A guard that is not dominated is kept, because a saved
historical row may carry any recipe with any contract value — that is exactly what
archival exists for.

Tests write the column directly (27 statements, §7.2) only to **seed** a saved
legacy record before the engine runs, standing in for a row created under an older
contract. Seeding is a fixture technique, not evidence about production: §6 proves
no production path rewrites the key, and the suite no longer constructs that
transition either (§7.3).

### 5.2 `advance` — the largest dominated group

`advance` (ENTRY `1377`) re-reads the row after every await: `1403` after
`root.mkdir`, `1413`/`1416` after `verify_snapshot`, `1461` after `validate_stage`,
`1496` after `submit_prepared_stage`. Each `execution_frozen` half is dominated by
`1377`; each `phase == "cancelled"` half stays (phase is not frozen by §6).

### 5.3 `dispatch` — one entry, nine re-checks

`3415` is the only guard before any await; `3418`…`3668` repeat after
`refresh_quota`, `refresh_cluster`, `ensure_cluster`, two prompts, `uv venv`,
`agent.session` and `agent.begin`. All nine are dominated by `3415`; `3668` needs the
immutability result (§6) because it sits after a turn was started, and that result
holds for every production path. The suite no longer constructs the transition that
would reach it (§7.3).

### 5.4 `observe_jobs` — settlement, then the legacy observation arms

`1913` settles every frozen job and continues, but only while
`exp["deleted_at"] is None`. A frozen record that is **deleted** and still owns a
`submitting`/`submitted` job therefore falls through to the observation path with
`iteration.enabled(exp)` false at the six sites §3 #15–#20, i.e. it is observed with
the saved legacy semantics. Today's delete command refuses that state
(`store.py:1186`–`1194`: terminal phase required, no `submitting`/`submitted` job,
no live action), but a saved historical row was written by older code, so its
preconditions are not a dominating guard. The six sites are therefore **READER** and
b keeps them; `1913` remains the SETTLE survivor.

### 6.4 What this proves, and what it does not

Because no writer changes `execution_contract`:

1. a guard that returned for a frozen record keeps returning for it, so a re-check
   after an await is decidable from the earlier guard in the same call (basis D) —
   **this is the only reason any DEAD row in this note is dead**;
2. no *production* call can flip the column mid-call, so a site that a flip would be
   needed to reach (`dispatch:3668`) is dead; the suite no longer constructs that
   flip (§7.3);
3. `Store.update` cannot change the key even accidentally, because the allow-list
   excludes it.

It does **not** say that a frozen record is a rare shape, or that a brief-driven
recipe implies contract 3: saved historical rows are frozen records. That is why
every non-dominated guard is kept.

the key each path documents. Two mutants confirm it fails when a store path drops
or rewrites the key (`contract["execution_contract"] = 2` and
`contract.pop("execution_contract")` at `885`/`1412` respectively).

### 6.6 No path can change it

All 13 writers preserve the key whatever value it holds; the creator always writes
3. Nothing to escalate from this subcard.
