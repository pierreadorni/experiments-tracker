# T1.3b transfer and publication writer map

Read-only source inventory for b7–b9, on the current `t1-archive-command-tail`
worktree. No policy or source behavior is changed here. The approved owner/episode
rules and separation of report readiness from artifact delivery are in
[t1.3b-rollout-design.md](t1.3b-rollout-design.md).

## b7 — execution transfers

`RemoteSlurmScheduler.transfer` (`src/experimenttracker/remote.py:260–305`)
receives an explicit identity or makes a UUID. Current call sites use deterministic
IDs: upload is SHA-256 of `experiment_id + evidence_revision + intent_id + "up"`
(around 444); terminal download is SHA-256 of `intent_id + ":terminal-delivery"`
(around 595). Nonterminal downloads pass `identity=None`, hence a fresh UUID.

The row identity is `execution_transfers.id`; saved scope/data are
`experiment_id`, `direction` (`up`/`down`), immutable encoded `payload` containing
remote settings plus resolved layout, `state`, `result` (bounded exception text or
cancellation text), and `updated_at`. The table has no explicit phase or evidence-revision column; the
transfer ID embeds evidence revision for uploads, while the immutable payload
layout records remote/local project and run paths and settings. The operation is an
awaited rsync/mkdir/move sequence. A preflight cancellation check occurs before and after layout resolution;
a polling loop checks cancellation while it waits.

The insert and payload conflict check share a transaction, but **no event/outbox
row is emitted**. Failure writes `pending` plus error text in a second transaction;
success writes `complete` and clears result in another. Those writes also emit no
event. `Store.cancel_experiment` (`store.py:882–929`) changes nonterminal transfer
rows to `cancelled` in the same command transaction as phase cancellation and
`experiment_cancel_requested`; there is no transfer-specific event. Cancellation
of the running coroutine raises `TransferCancelled` and relies on that store path
to persist cancellation.

**Replay hazard to preserve and expose:** `INSERT OR IGNORE` validates only that a
prior row's payload matches, then proceeds to execute `operation()` regardless of
prior state. Thus a prior `complete` row with the same ID is replayed as another
external operation without returning to `pending`; the persisted state stays
`complete` while the operation is in flight. Do not interpret `complete` as proof
that no current external operation exists. Tracking needs to model the actual
retry/replay responsibility, but this inventory does not choose or alter that
policy. Also, nonterminal download UUIDs are not stable across an uncertain call.

**Bounded b7 plan (<500 source+tests):** wire the transfer mapper and its focused
identity/replay/owner-cycle tests at the transfer insert and each outcome write in
`remote.py`; wire cancellation settlement in `store.py` using the same exact row
ID/episode. Include same-payload complete-row replay, payload conflict, exception
pending, cancellation race, and repeat cancellation. Require a state-change event
in the same transaction for remote-created/updated transfer rows; retain the
existing cancellation event transaction. Keep retry/dispatch semantics unchanged.

## b8 — report-version creation/state and artifact registration

`report_versions` is keyed by `(experiment_id, version)` with saved `request_id`,
`document`, `state`, `error`, `artifact_ids`, `report_artifact_id`, and creation /
update timestamps (schema in `store.py:230`). It has no phase or evidence-revision
column; output identity/scope is captured by `artifact_ids` / `report_artifact_id`,
whose artifact IDs incorporate the experiment evidence revision. `working_report` replays by
`(experiment_id, request_id)`, rejects changed document bytes, and creates the
next version in `queued` state; `initial_report` uses version 1 and
`initial-report:<experiment_id>`. Both insert and `report_requested` event share a
transaction (`store.py:1620–1660`). Callers include workflow final report creation,
controller `update_report`, and iteration working-report creation (`workflow.py`,
`controller.py`, `iteration.py`). The iteration producer passes its existing job
transaction through `_db`, so report insert/event are atomic with that job update.

`Store.report_state` writes state/error/time and emits `report_updated` in one
transaction; a `ready` state for version >1 also inserts the `report_ready` inbox
item there. It silently returns if the experiment is cancelled. `artifacts.register`
(`artifacts.py:279–330`) deterministically IDs artifacts by experiment, evidence
revision and name; records local path, digest, size, media type and validity. With
`report_version`, it also stores the ordered artifact ID list and report artifact
ID while setting version `publishing`. Artifact rows, report metadata, and
`artifacts_registered` event share the supplied transaction (or its own transaction);
no event is emitted if nothing changed. Iteration passes its job transaction;
report rendering generally owns a separate transaction.

b8 source scope is store report request/readiness helpers plus artifact registration
state transition, including callers that already pass `_db`; preserve immutable
request/document and output identities. **Bounded plan (<500 source+tests):** split
request/version creation and its replay tests from artifact/version registration
and state-change tests if measured combined integration exceeds budget. Assert event
and outbox rollback at each affected transaction, same-request replay, conflicting
document, and ready inbox idempotence. Do not include final experiment completion
or delivery acknowledgements (b9 / separate delivery identity).

## b9 — final publication completion/failure and cancellation

`Workflow.publish` (`workflow.py:3893–3997`) moves the experiment to `publishing`,
checks registered evidence, queues/reads the final report version, registers
`report.html`, then marks publish stage and experiment `complete`, inserts
`result_ready` inbox and emits `result_ready` in one transaction. The phase change
and completion event are atomic. It returns while report state is not ready or while
current gateway delivery is incomplete. A failed report version may return the
experiment to interpretation for correction (direct SQL plus `report_correction_required`
event in one transaction), or fail the experiment through `fail()`.

`advance_reports` (`workflow.py:4000–4078`) selects queued/building/publishing
versions, changes queued to building via `report_state`, builds outputs, registers
them (publishing), checks registered outputs, then sets ready via `report_state`.
Exceptions set failed via `report_state` and enqueue a failure notification through
`Store.notify`. Cancellation excludes cancelled experiments from the query and
checks cancellation after report generation. These final report state transitions
already use `report_updated` events; the publication completion/failure transaction
must satisfy/abandon the matching report-version obligation without conflating it
with experiment advancement or artifact delivery. `Store.cancel_experiment` fails
all queued/building/publishing report rows in its cancellation transaction, but
only emits generic `experiment_cancel_requested`, not per-version `report_updated`.

**Delivery boundary / current coupling:** `advance_reports` only marks a version
ready after selected artifacts have `remote_published=1` when a gateway is enabled;
`Workflow.publish` also waits for all current-revision artifacts. The approved design
assigns publication responsibility to report readiness and keeps remote delivery
under its own artifact identity. Preserve readiness semantics as approved, but do
not key a publication obligation to `artifact_id` or treat readiness as upload
acknowledgement. The delivery writer is `gateway_client.upload_artifacts`: it
persists `remote_published=1` and emits `artifact_published` in the same transaction
after verifying exact artifact ID, SHA-256, size and availability. Failed uploads
have only in-memory retry/error tracking; the durable artifact row remains
`remote_published=0`. Delivery has an exact artifact ID and existing event, so any
separate delivery obligation belongs to the artifact-delivery decision, not b9.

**Bounded b9 plan (<500 source+tests):** wire report-version ready/failed outcomes,
final publish completion/failure, and cancel settlement by exact `(experiment_id,
version, request_id)` in their existing transactions; use `report_updated`, existing
final result/cancel events and outbox rows. Keep version readiness distinct from
remote artifact delivery. Test queued/building/publishing cancellation, failure,
ready replay, final completion replay, queued report on terminal/archive paths, and
atomic rollback. If scope exceeds budget, split cancellation from workflow final
settlement; do not omit either writer group.

## Writer gaps to carry into implementation

- Transfer insert, retry-pending, completion, and transfer cancellation currently
  have no exact transfer event; cancellation has only the enclosing generic event.
- Report cancellation directly changes multiple `report_versions` rows without
  per-version `report_updated`; it does have the enclosing cancellation event.
- Artifact registration emits its generic event only when a row or report metadata
  actually changes. Gateway upload acknowledgement does emit `artifact_published`
  in the same transaction as `remote_published=1`.
- Report readiness presently waits on delivery; the approved obligation identity
  remains report request/version, while artifact delivery remains a separate saved
  identity. Do not silently turn one into the other.
