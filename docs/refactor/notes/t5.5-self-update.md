# T5.5 Reassessing the self-update subsystem

Audit F11 says `maintenance.py` "exists mainly because restarts are risky". This note
measures the subsystem at `b8b0fad` (after T5.2), checks which guards answer failures
recorded in this repository, and proposes follow-up cards. The private installation
record was not read. Only public notes and the todo log are cited.

## 1. Current shape and size

| Part | Lines | Notes |

| Other Python touch points | ~140 | 5 `/api/maintenance*` routes (`api.py` ~56), `serve --release` (`cli.py` ~10), relay command kind and receipt (`publish/commands.py` ~20), `maintenance` projection (`projections.py`, `gateway_client.py` ~20), schema 21 (`store.py` 12), 17 `blocked()` gate calls, `runner.py` launch hook |

In total there are about 880 production Python lines, about 265 UI lines and about 524 dedicated test lines.

**States.** Release: `preparing → testing → ready | failed` (4). Operation:
`waiting → backing_up → verifying_backup → restarting → starting → verifying →
complete`, plus `failed`, `blocked` and `cancelled` (10). Transitions are strictly sequential.

**Owner effort per update today.** An agent commits and runs `maintenance prepare --detach`.
That runs one full `make check` and needs no owner action. If the
Worker changed, the owner publishes it separately. Then the owner makes two clicks: **Install update…**
and **Authorize installation**. Rollout-specific preconditions are outside the updater. The T5 rollout,
step 1, asks for a manual offline backup and a `drain_inventory` run before installing.

**T5.2 changes.** The Worker's 183-line `maintenance.ts` and its executor routes are gone
(T5.2h/i). Install is one relay command kind (`maintenance`) that the executor receives through
`publish/commands.py`. Status is one aggregate projection, `maintenance`. One special case
remains: the coordinator still has its own relay publisher (`publish_progress`, about 35
lines). It reads the revision manifest and PUTs the projection, because the owner is
down mid-handover. T5.2g rewrote it.

**Prerequisite for the claim that "restarts are routine"**: the T5.2 log records a production shutdown race
(an `ensure_branch` thread writing after the store closed). Similar `to_thread` calls in `controller.py`,
`research/dispatch.py` and `research/settlement.py` remain unchecked. A restart path must be clean
before any guard is relaxed.

## 3. Options

**A. Keep as is.** Deletes nothing. No new risk. Owner effort: two clicks. Cost: about 880
Python lines and about 265 UI lines to maintain, a cross-version `identities()` contract
that every future schema card must preserve, and a 24-hour stall when a question goes unanswered.

**B. Simplify to "tested release, authorized restart, health check" (recommended).**
Keep the release folder and `make check` receipt, the durable install command, the detached
coordinator, one verified backup, the narrowed dispatch hold, and the health check. The health
check confirms a new boot id, the expected commit, one healthy tick, `agent_ready` and no
`executor_error`. Delete the identity baseline and `/internal` identities, the
configuration hashing, the preparer PID tracking and `--detach`, the `preparing`/`testing`
states, the separate `verifying_backup` state, the two dead blockers, the rehash in
`verify_release` (the 0400 receipt and the folder are the evidence), and optionally
`publish_progress`. Estimated: about −200 to −250 production Python lines, about −80 test lines and about −20
UI lines. The release states become `ready | failed` and the operation states become `waiting → restarting →
starting → verifying → complete | failed | blocked`. Risk: a migration that rewrites identities
would no longer block at handover, so the new migration test (card T5.5b) must cover it. Owner
effort: unchanged, two clicks.

**C. Replace with a documented manual procedure and a small health check.**
Delete `maintenance.py`, the routes, the relay kind, the projection, `ExecutorUpdate.tsx`,
the smoke test, `test_maintenance.py` and the 17 `blocked()` calls. Keep schema 21 tables as read-only
history. That removes about 880 Python lines, about 265 UI lines and about 524 test lines. Add about 80 lines: a `restart-check` CLI
(blockers, exit nonzero) and `health --wait`. Then document this sequence: `git archive` and `uv sync` into a release
folder, `make check`, SIGTERM (the shutdown backup), and `setsid … serve --release` from the folder. Risks: no phone
authorization; no dispatch hold while waiting for a window, so new turns keep starting;
an owner started from an agent's shell can die with that session; serving from a
mutable checkout breaks lazy imports. Every step depends on operator discipline. Owner effort: shell
access or an explicit chat authorization, then 5–6 commands per update, run by the owner or by an
agent they authorize.

## 4. Recommendation

Choose **B**. With routine restarts, the owner still benefits from authorizing installs on a phone
and from immutable tested bytes. Those two features are most of the safety and all of the convenience.
The ceremony to remove is concentrated in cross-version identity comparison, tracking of
preparation progress and dead blockers. C deletes more but moves the risk onto operator discipline,
on a host where AGENTS.md forbids a permanent supervisor.

Follow-up cards, in order:

1. **T5.5p Shutdown races** · S. Apply the `finish_threaded` wait (T5.2) to the
   remaining `to_thread` calls in cancellable loops: `controller.py`,
   `research/dispatch.py` branch checkout and `research/settlement.py` commit.
   Acceptance: a restart scenario cancels each loop mid-call, and no write happens after the store
   closes. Tests stay stable across repeated runs.
2. **T5.5a Narrow maintenance blockers** · S, `maintenance.py`, `tests/test_maintenance.py`.
   Drop the `restart steering` and `pending_request` blockers. Apply owner decision 2 to
   running turns and shorten the boundary deadline from 24 hours to the chosen value.
   Acceptance: an unanswered C4 question does not hold an install. An uncertain submission
   or unfinished transfer still holds it. Restart-scenario tests prove that the question survives.
3. **T5.5b Drop the identity baseline and configuration hashing** · M, `maintenance.py`, `api.py`
   (`/internal`), `store.py` tests, `tests/test_maintenance.py`, `docs/executor-updates.md`.
   Replace the baseline with a migration test: every schema step preserves `jobs.intent_id/job_id`,
   action and turn thread/turn ids and pause controls on a seeded database. The health check
   becomes boot id, commit, a healthy tick, `agent_ready` and no executor error. Ship it
   compatibly: the *old* coordinator still compares identities, so keep `/internal`
   `identities` for one release, then delete it in the next. Acceptance: the real
   two-process handover test still passes, and `rg "identities\(" src` finds only the
   compatibility shim, which a named later step deletes.
4. **T5.5c Collapse release preparation** · S/M, `maintenance.py`, `api.py`,
   `ExecutorUpdate.tsx`, `maintenance-smoke.mjs`, docs. `prepare` runs in the foreground
   and registers only `ready`/`failed`. Delete `--detach`, preparer PID and process identity,
   the reaper in `launch()`, the `preparing`/`testing` and `verifying_backup` states and the
   receipt rehash. Use one detached-spawn helper for the two remaining spawns (t1-reduction-audit item 8).
   Acceptance: a failed `make check` never yields `ready`. Repeating `prepare` for a ready commit
   is a no-op. The UI shows only the states that remain.
5. **T5.5d (if decision 3 = drop)** · S. Delete `publish_progress`. The new owner
   republishes `maintenance` on startup, and the UI shows "Update may need attention" when an
   active operation's observation is older than 10 minutes and the executor is offline.
   Acceptance: the existing stale-status smoke case covers it.

Estimated total for cards 2–5: about −250 production lines and −100 test lines, with no change to the owner's two clicks.

## 5. Owner decisions (recommended default first)

1. **Keep phone-authorized installation (B) or move to a manual procedure (C)?**
   Default: **B**.
2. **Should an install wait for running agent turns?** Default: **wait, with a 2-hour deadline**
   (today 24 hours). Then refuse and release the hold. Do not interrupt a turn: C4 would resume it, but the
   interrupted turn's spend is lost. The alternative is to stop at the next settled boundary only for
   uncertain or submitting work.
3. **Keep the coordinator's own progress publisher?** Default: **drop it** (T5.5d). The offline
   indicator and the stale label carry the same information.
4. **Retire the identity baseline only after a migration test exists (T5.5b ordering)?**
   Default: **yes**, as a two-release compatible removal.
