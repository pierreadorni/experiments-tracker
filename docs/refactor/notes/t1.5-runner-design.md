# T1.5 independent periodic tasks — coordinator design

Status: design approved with conditions by Opus 5.5 after revision.
Review base `42829f4`. Owner decisions 1–6 are approved as recorded in
[t1-owner-decisions.md](t1-owner-decisions.md); preceding harness/obligation/
resolver dependencies still apply before implementation.

## Outcome and initial coordinator plan

Replace the sequential production tick loop with isolated periodic coroutines,
keeping one SQLite authority/ownership lock, persisted intents, C1 error policy,
existing agent ownership and unchanged scientific contracts. The initial plan
proposed shared step methods, a manual tick adapter, independent publication and
dispatch/control-based health. Opus run `670e31fa-b66c-4a5a-a9ec-1f31460bc6b2`
decided **REVISE**, narrowing the plan as below. This note implements that review,
not an exception to owner rules.

## Reviewed design

1. Add `engine/runner.py` (and package initializer), owning named periodic loops,
   stop event and per-task internal last-success/error state. Each loop catches
   and logs ordinary exceptions by task name; cancellation propagates. Use current
   cadence settings/constants only; add no schema/config/env keys or public status
   fields. Replace the API tick loop, never run both. Startup happens once before
   loops; periodic steps never call `start()`. Only manual `tick()` retains lazy
   startup for compatibility.
2. Retain `Workflow.tick(force_observe=...)` as a manual adapter over shared steps,
   preserving the original sequence. Control code currently straddles observation:
   before/after-observation helper fragments must therefore remain separately
   callable by this adapter. A production `step_control` may compose those
   fragments without observation, under its lock. Do not silently move all prefix
   and suffix code together in the manual adapter and claim unchanged ordering.
   Extract narrow helpers where needed to preserve exact callback/maintenance/
   observation placement; no new execution behavior in the mechanical subcard.
3. Use one primary-agent `asyncio.Lock`. Entire control, research and supervisor
   steps take it, preserving the sequential loop's check-then-act exclusion across
   awaits. Read `blocks_dispatch` and act on it inside the same control step;
   retain its suppression of experiment rows and conversation/title/controller.
   Keep all current global role exclusions until T1.6. Observation, watchdog,
   retention and backup never take this lock. This is not mixed-role concurrency.
4. Observation handles cluster refresh and existing saved-job observation/accounting.
   After T1.4a, the resolver alone owns `submitting` rows without IDs; observation
   skips those rows. Both paths must respect the already-existing submission lock:
   never reconcile a submitting intent while an external submission is in flight.
   Adoption uses `WHERE intent_id=? AND state='submitting' AND job_id IS NULL` and
   checks rowcount before emitting adoption. Queries may run outside unrelated
   admission locks; re-check current durable state transactionally before commit.
   Do not infer absence, submit a replacement or emit a second adoption event.
5. Apply the exact current maintenance gating. Before the `blocked()` return,
   observation, input replies and agent draining continue. After it, steering,
   restart, repair, local reports, experiment advancement, watchdog, cleanup,
   research, supervisor, retention and backup remain gated as today. A skipped
   step counts as successful for health; no maintenance-policy widening here.
6. Keep `advance_reports` and `queue_late_reports` inside control, in current order,
   so revision changes cannot race report construction. The card's independent
   publication task is the already separate GatewayClient bridge: retain one
   bridge owner, projection-before-artifact ordering and existing command polling.
   Do not create a second publisher or move report construction out without proof.
7. Keep `maintenance.launch()` single-flight after a successful control step,
   including when its maintenance gate skipped later work; the current outer API
   loop calls launch after a normal return from tick. Failed control must not be
   reported as a successful complete engine pass.
8. Preserve `/healthz` semantics using existing `last_tick`/`last_tick_error` fields.
   `last_tick` is the oldest last-success time across tasks extracted from the old
   sequential tick (control, observe, research, supervisor, watchdog, retention,
   plus resolver if T1.4 has integrated it there). A latest failure in any such
   task sets the existing error. Exclude backup, which was already background.
   An empty heartbeat or healthy control alone cannot hide hung observation.
   An independent bridge retains its current status, not a second heartbeat API.
9. Loops wait on the stop event rather than bare interval sleeps. Shutdown sets
   stop/closing first, forbids new admissions and stops new scheduling. Await
   owned in-flight threaded work, especially retention and backup; cancelling an
   awaiting task does not stop its thread. Cancel only safe waits/async-only work
   as the existing lifecycle permits. Then close bridge, call workflow.close to
   settle owned checks/agents/backup, close SQLite and release the ownership lock.
   A task cancellation never proves an external action absent. Do not close the
   store while an owned task/thread can still write.

## Ordering and implementation split

Follow-up Opus run `87b6f47d-e098-40f2-b25a-3a5c1e4bc217` gave the final decision
**APPROVE WITH CONDITIONS**, accepting these clarifications:

- The manual adapter needs separately callable control fragments to retain the
  observation point (rule 2); a combined control method cannot preserve that order
  on its own.
- The guarded-adoption/submission-race protection must land **before or with**
  production runner activation, not in a later safety-fix commit.
- Health includes the resolver if it belongs to the then-current sequential tick,
  rather than pretending the pre-T1.4 source is still the complete task set. Fix
  and document that health-counted set in T1.5a; activation cannot redefine it.

Proposed safe ordering, each measured below 500 changed source/test lines:

- **T1.5a (F mechanical):** extract shared helpers/steps and tick adapter, preserving
  exact old behavior/order and maintenance gates; targeted regression tests.
- **T1.5b (S safety groundwork):** add or verify the submitting-owner split,
  submission-in-flight exclusion and compare-and-set adoption with race tests,
  while production remains sequential. If T1.4 already establishes them, verify
  and reuse them rather than duplicate a resolver.
- **T1.5c (S activation):** runner, API lifecycle, health, primary-agent exclusion
  and safe shutdown, with focused activation tests. If additional isolation/
  recovery scenarios exceed budget, split those explicitly before acceptance,
  but mandatory ownership/race/shutdown gates cannot be postponed past activation.

No step absorbs T1.6 admission policy or T1.7 mechanical module splitting. None of
these proposals changes todo-card order or authorizes implementation by itself.

## Verification and constraints

Event-controlled fake services, T1.2b clock/harness and real temporary SQLite prove:

- Blocked observation/backup does not stop unrelated control, watchdog or bridge;
  health nevertheless becomes 503 for stuck formerly-sequential observation.
- Task failures are isolated and the next period can recover. Existing C1
  experiment backoff and the three scenario ports still pass.
- Active submission is never reconciled/adopted prematurely; exact saved IDs are
  adopted once with one event, no false hold and no duplicate external call.
- Maintenance gates and primary-agent exclusion are unchanged; exactly one
  runner and one bridge exist; maintenance launch is preserved.
- Shutdown with active retention/backup/checks/turns leaves no SQLite-writing owner
  after store close, without interpreting cancellation as external absence.

No real timed sleeps as success evidence; timeouts are failure detectors. Run
focused tests, Ruff and full Python suite before each accepted subcard, outside
restrictive subprocess sandboxes. No live activation, new permanent service,
scientific hashing or new reason/schema/config vocabulary is authorized.
