## Relevant design constraints

- C2 (`design.md`) requires obligation open/close in the same transaction as the
  saved source transition. `core/obligation_sources.py` supplies `open_episode`,
  `latest_episode`, `satisfy_episode`, and `abandon_episode`; it requires the
  caller's transaction and episode advancement only with a proven source
  transition. There is no jobs-specific mapper yet.
- Rollout decisions make jobs backend-owned during admission/uncertain
  submission and external-owned only after an exact scheduler ID is saved.
  Fulfillment satisfies; failure, cancellation, and supersession abandon.
  Reconciliation itself cannot prove external absence or permit retry.
- Job obligation ID should be `job:<intent_id>` as the earlier inventory
  proposed, but b1's episode helpers mean callers should use a `job` source
  episode (`job:<intent_id>:<episode>`) consistently. Initial tracking is
  episode zero; unchanged replays retain it; responsibility changes are proven
  inside the source transaction. Do not bypass the helper with a hard-coded
  terminal ID.
- The saved source row must be selected inside the same `store.tx()` before its
  mutation; select it again after mutation, then update obligation and emit the
  existing event before commit. Snapshots captured before awaits are not proof
  of the current row. State labels alone do not establish scheduler liveness.

## Failed state, terminality, and saved scheduler identity

`workflow.observe_jobs` explicitly polls some contract-3 rows with
`jobs.state='failed'`: scheduler state null/nonterminal, or exit code missing.
`steering.process_restarts` includes failed rows with a saved ID unless their
scheduler state is in `TERMINAL_JOBS`; cancellation also selects failed rows with
IDs and observes them unless the saved scheduler state is terminal. This covers
workflow validation failure before Slurm ends, and unknown/accounting-pending
observations. Therefore the pure source mapping must classify from the saved row
and exact scheduler terminal facts, not `state` alone:

- `submitting`, no `job_id`: backend/reconcile for the saved intent; unresolved
  remains open.
- exact saved `job_id`: external job episode. `submitted`, and failed/unknown or
  failed/nonterminal scheduler observations, remain open. Replays do not reopen
  terminal episodes.
- exact `COMPLETED` with a saved exit code is externally terminal: `0:0`
  satisfies the external execution obligation, even if later output validation
  leaves `jobs.state='failed'`; nonzero exit abandons it. This tracks scheduler
  execution settlement, not scientific stage acceptance.
- exact terminal scheduler failure/cancellation: abandon the external episode.
- cancelled experiment with a live/unknown scheduler row still has an external
  settlement obligation until exact terminal accounting is saved. Do not let
  experiment phase or a cancellation request erase it.
- Never use `scheduler_state` strings alone without the existing per-path
  accepted terminal set and required accounting (notably `COMPLETED` with missing
  exit code remains unresolved). Preserve contract-specific historical behavior.

These are mapping recommendations only; avoid inventing new reasons, states,
config, terminal vocabularies or error codes. Tests should include failed state
with missing/nonterminal scheduler state, failed with exact terminal scheduler
state, successful accounting while validation is pending, and unknown-ID
reconciliation without retry/closure.

## Contract-3 agent pseudo-job and missing exact link

`iteration.queue_agent` records a pseudo-job before a managed turn. It is found
by `(experiment_id, stage_id, attempt=evidence_revision)` and is selected by
`workflow.agent_stage` for an action whose `phase` is `agent:<stage>`. The
corresponding `agent_actions` row has phase/evidence revision/thread/turn, but
the job schema has no `action_id`, and the job insert records no exact action ID.
`queue_agent` emits `agent_stage_intent`; action creation/dispatch occurs on the
workflow path separately. Several historical/repair/continuation actions can
share phase and evidence revision, so the composite stage/revision is an attempt
association, **not an exact durable agent-action identity**. Do not make a
Slurm-style `job` obligation for this row, do not infer an agent turn from the
pseudo-job alone, and do not invent a schema link in b5/b6. The exact
`agent_turn` obligation belongs to the saved `agent_actions.id` lifecycle in
b2b–b4. If no exact action exists while pseudo-job/stage says running, record it
as an uncovered source/liveness diagnostic for later resolution; do not claim
that agent-turn obligation coverage includes this pseudo-job. The bulk cancellation
writer can also mark pseudo-jobs cancelled after no active action, reinforcing
that their state does not prove managed-turn terminality.
