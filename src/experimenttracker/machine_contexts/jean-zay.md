# Jean Zay execution context

The agent and workflow owner run on acacia. Jean Zay receives files via rsync and runs ordinary Slurm jobs. No resident executor, Codex credential, web server or polling daemon is installed there. SSH calls are short and automatic monitoring is at most once every ten minutes. Use `ssh jz` for essential read-only discovery; avoid polling loops.

The configured remote folder is a base. Templates `{remote_project}` and `{remote_run}` resolve to separate per-experiment/revision checkout and output folders under that base's `.experimenttracker/executions/`. `{local_project}` is the actual acacia working checkout (possibly a worktree); `{local_run}` is its saved run output directory. Use placeholders rather than hard-coded old worktree paths. `{host}` is the saved SSH alias. Agent tools can set both rsync commands; new projects start with empty commands. Do not sync .venv, secrets, credentials, caches, datasets or unrelated experiment trees. No shell expansion occurs inside transfer templates. Use shell quoting for spaces and rsync include/exclude patterns.

Example up command:
`rsync -az --exclude=.git/ --exclude=.venv/ --exclude=.local/ --exclude=.experimenttracker/ {local_project}/ {host}:{remote_project}/`
Example down command (selected TensorBoard events and light plots):
`rsync -az --include=*/ --include=*.tfevents* --include=*.png --include=*.svg --exclude=* {host}:{remote_run}/ {local_run}/`
The executor separately returns required declared small outputs, owned stdout/stderr and checkpoint provenance. Store valuable checkpoints under EXPERIMENT_ROOT and declare local_outputs; those bytes stay on Jean Zay. Declare regenerable feature caches in temporary_outputs under EXPERIMENT_ROOT/temporary/; they are not hashed or published and are removed only after the report is ready. EXPERIMENT_SHARED_PROJECT points to the configured base for explicitly shared caches/assets; automatic cleanup never touches that base. Datasets can remain elsewhere on Jean Zay.

Observed by read-only discovery on 2026-10-13: Slurm partitions included cpu_p1, gpu_p13, gpu_p2/p2l/p2s, gpu_p5, gpu_p6 (H100), plus bounded prepost/compil/visu partitions. This account had uel@v100, uel@a100 and uel@h100 associations. These are discovery evidence, not guaranteed current authorization. Read the supplied fresh snapshot and sbatch --test-only result; partition presence does not grant access. GPU partition, account, QoS, constraint, CPU/memory and runtime must be chosen together. Do not infer GPU architecture solely from a partition name.

$HOME is small shared Lustre storage (observed 3 GB); use $WORK for source/input/output, $SCRATCH for temporary high-throughput data and $STORE for long-term storage. Scratch has a cleanup policy; do not rely on it for permanent checkpoints. Login-node /tmp and /var/tmp are local and have unconfirmed retention; they never hold authoritative workflow state. Resolve variable names on the actual remote login environment. Common datasets are already provided through $DSDIR (check its value and contents; do not assume $DS_DIR is an alias). For example the researcher's FLAIR workflow used "$DSDIR/HuggingFace/IGNF/FLAIR-HUB".

Login nodes have HTTP proxy access; compute-node Internet access is restricted. Prepare downloads/dependencies through supported login-node/module workflows. Substantial setup and validation belong in allocated jobs. Bash module setup can require the login environment; stage scripts should initialize module support explicitly if needed. Do not copy an acacia virtual environment. For example an existing workflow used `module load pytorch-gpu/py3/2.8.0`; verify availability before selecting it.

An illustrative existing V100 request used 12 CPUs, one GPU, one task, constraint v100, twelve hours and account uel@v100. Select the matching authorized partition/QoS using live discovery. Agent .sbatch scripts are supported: declare script and structured resources consistently. The executor overrides resource directives with those structured resources, plus its exact job name/comment, log paths and remote working directory. No arrays, nested submissions or script-controlled scheduler dependencies. The .sbatch body runs from EXPERIMENT_PROJECT; sources also exist in EXPERIMENT_SOURCE and results go in EXPERIMENT_ROOT. Scripts should fail on scientific validation errors.

Live `sbatch --test-only` on 2026-10-16 confirmed that the IDRIS submit plugin rejects `--mem`, `--mem-per-cpu` and `--mem-per-gpu`. Omit these directives. The remote adapter omits `--mem`; memory follows the cluster's CPU/GPU allocation policy. `memory_mb_per_job` remains a planning estimate, not an explicit reservation. Choose enough CPUs/GPUs for the expected memory requirement. An optional executor memory ceiling holds remote submission because it cannot be enforced through these forbidden options. See http://www.idris.fr/docs/jean-zay/slurm/exec_alloc-mem.
